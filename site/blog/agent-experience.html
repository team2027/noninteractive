Agent Experience Is the New UX

We ran 130 AI agents through an interactive CLI wizard. The results changed how we think about tool design.

Round 5, Thursday afternoon. Ten AI agents, all running eslint --init in parallel. No documentation, no skill file, no guidance beyond a one-sentence prompt: "use npx noninteractive to complete npx eslint --init."

They discovered the tool from --help, figured out the API on their own, and started completing the wizard. Some agents nailed it in ten minutes flat. Then the killing started.

agent 3 ran ps aux | grep ptybridge, found pid 57278 — a perfectly healthy process belonging to another agent. Thought: "these stale processes could be interfering." Ran kill 57278 57248 57247. Three agents just lost their sessions.

What followed was a death spiral. Agent A kills agent B's process. Agent B sees its session is dead, assumes something is broken, runs ps aux, finds agent C's processes, kills those too. Agent C does the same to agent D. Meanwhile, agents 1 and 5 finished the task in ten minutes, blissfully ignorant of the carnage. They never once checked on other sessions. They just did their job.

Round 5 was our worst round. Average 86 tool calls, ten minutes per agent. But it taught us more about designing tools for AI agents than any user study ever taught us about designing for humans. And the lessons apply far beyond our CLI wrapper — they apply to every developer tool that an agent might touch.

What Is Agent Experience (AX)?

User Experience (UX) is a solved vocabulary. We know what it means to design for humans: intuitive navigation, clear visual hierarchy, helpful onboarding. But what happens when the user holding the keyboard isn't human?

Agent Experience (AX) is how well a tool works when the user is an AI agent. It's the design surface that matters as LLMs become primary consumers of developer tooling — not just CLIs, but REST APIs, SDKs, build systems, package managers, database clients, infrastructure tools. Anything an agent might call.

And it turns out, almost everything we know about UX is wrong for AX. Humans read documentation before starting a task. Agents guess, fail, and learn from the error message. Humans see visual cues: color, layout, spatial hierarchy. Agents see plain text. Humans type one command, think, type another. Agents chain ten calls in milliseconds.

Humans recover from errors through intuition and context. Agents recover through error messages — and only through error messages. If your API returns 400 Bad Request with no body, the agent is lost. If your CLI says "invalid argument" without showing what a valid argument looks like, the agent will try ten more invalid variations before giving up.

AX is the new frontier. Whether you maintain a CLI, an API, an SDK, or a build tool — the next wave of your users will be AI agents running CI pipelines, configuring projects, managing infrastructure, and writing code. Your tools need to be designed for how agents actually behave, not how humans expect them to.

The Methodology: ax-eval

We needed a way to systematically test agent experience. Not a benchmark. Not a static eval. Something that captures the chaos of real agent behavior at scale. We built a framework called ax-eval, and it's a process anyone can apply to any developer tool.

The setup is simple: spawn N agents in parallel, each with an identical minimal prompt. No documentation, no examples, no hand-holding. Just a single sentence describing the task. Then watch what happens.

In our case: 10 Claude Code agents, each given "use npx noninteractive to complete npx eslint --init, and create a valid eslint config." Each agent runs in its own session with full shell access. They can install packages, read files, run commands, kill processes — anything a developer could do. They share the same machine, which means they share the same environment. This is intentional. Real agents in real production environments will collide.

After each round, we collect every transcript. We analyze the patterns — what commands agents tried first, where they got stuck, what caused cascading failures. Then we fix the tool, ship a new version, and run another round.

Thirteen rounds. 130 total agent runs. 17 versions shipped. Each round revealed something we didn't expect, and each fix was validated by the next ten agents. No human beta testers. No surveys. No focus groups. Just agents, failing and succeeding, over and over.

The transcripts are brutal in their honesty. Agents don't politely work around your bugs. They expose every sharp edge, every ambiguous error message, every missing feature — usually within the first 30 seconds. If you maintain a developer tool and you aren't testing it with agents yet, you're flying blind.

Five Universal Principles of Agent Experience

1. Agents learn from errors, not documentation

Here's a data point that should change how you think about developer tools: across our later rounds, 0 out of 10 agents ran --help before trying a command. Zero. They skipped documentation entirely and went straight to guessing.

This isn't laziness — it's optimal strategy. An agent's workflow is: form a hypothesis about the interface, try it, read the error, adjust. The error message is the documentation. It's the only thing the agent reads before its next attempt.

This principle applies far beyond CLIs. If your REST API returns a bare 400 Bad Request, agents will flail. If it returns a structured error with the missing field and a valid example, they self-correct immediately. If your SDK throws TypeError: invalid argument, agents spiral. If it throws TypeError: expected string for 'name', got number. Example: client.create({name: "foo"}), they fix it on the first retry.

In our tool, early errors looked like this:

before
Error: unknown option '--name'

Agents would get this and try -n, then --session-name, then --id. Five attempts to discover a syntax that existed but wasn't communicated. We changed every error to include a working example:

after
Error: unknown option '--name'
hint: to start a named session, use positional args:
noninteractive start eslint npx eslint --init

100% correction rate on next attempt. Every single agent read the hint, used the example, and moved on. The pattern was so reliable that we started treating error messages as micro-tutorials — each one a complete lesson in the correct interface.

The universal lesson: your error messages are your real API documentation. README files, wiki pages, even --help text — agents skip all of it. Put a working example in every error. If you do nothing else from this article, do that.

2. Agents are destructive when confused

When an agent can't figure out what's happening, it doesn't wait patiently. It escalates. And the escalation follows a remarkably consistent pattern across every tool we tested.

First, the agent retries the same action. Then it tries variations. Then it starts investigating — listing processes, checking files, reading logs. Then it starts fixing — killing processes, deleting files, resetting state. We watched agents pkill each other's processes, rm -rf session directories, and attempt to kill -9 system processes. Not malicious. Just desperate problem-solving.

This isn't unique to our tool. If your database client hangs without feedback, agents will kill the process and retry. If your build tool produces ambiguous output, agents will rm -rf node_modules and start over. If your API returns timeouts without status, agents will spawn parallel requests until something breaks. The pattern is universal: confusion leads to destruction.

In round 5, this combined with parallel execution to create the death spiral. Ten agents sharing a machine, each one capable of killing the others' sessions. The ones that finished quickly were fine. The ones that got confused became serial killers.

The fix wasn't preventing destructive actions — it was eliminating the confusion that triggered them. We made session state obvious and queryable. We added clear status messages so "waiting for output" didn't look like "broken." We added the --wait flag so agents could block until there was real new output instead of polling in a tight loop and concluding the tool was stuck.

The universal lesson: make your tool's state obvious at all times. If an agent can't tell whether something is working, hanging, or failed, it will assume the worst and act accordingly. Status endpoints, progress indicators, explicit timeouts — anything that answers "what is happening right now?" prevents the destructive spiral.

3. Test with 10 agents, not 1

A single agent test tells you if your tool works. Ten parallel agents tell you if your tool scales.

With one agent, everything looked fine. The tool worked, the wizard completed, the config was generated. Ship it. But with ten agents running simultaneously, we discovered: session name collisions when two agents picked the same name, socket interference when sessions overlapped, race conditions in file writes, and the death spiral when confused agents started killing each other's processes.

None of these bugs appear with a single agent. They're emergent properties of parallel execution — and in production, agents always run in parallel. Your CI pipeline runs multiple agents. Your deployment system orchestrates concurrent operations. Your coding assistant might spin up multiple sub-agents for different tasks.

This applies to any developer tool. If your API uses shared state — a database, a file system, a cache — parallel agents will find the race conditions. If your CLI writes to a predictable path, parallel agents will collide. If your SDK holds locks, parallel agents will deadlock.

The universal lesson: your testing methodology should match your deployment reality. If agents will use your tool in parallel, test with parallel agents. The bugs you find will be completely different from single-agent testing, and they'll be the bugs that matter most in production.

4. Agents try features that don't exist — that's your roadmap

Across rounds 8 and 9, something remarkable happened: 10 out of 10 agents tried flags that didn't exist. Every single agent tried --name to name their session. Every single agent tried --cwd to set the working directory. These weren't in the help text. They weren't in any documentation. The agents just assumed they should exist.

This is implicit user research at scale. When every agent independently tries the same non-existent feature, it's not a bug in the agents — it's a missing feature in your tool. The agents are telling you what your interface should look like, based on their understanding of what a reasonable tool would offer.

We implemented both flags. The next round: zero errors on the start command. The friction that had cost every agent 1–2 extra calls simply vanished.

This principle extends to any tool. If agents consistently try POST /api/users before discovering your actual endpoint is POST /api/v2/accounts/create, the agents are right and your API is wrong. If agents try build --target production and your flag is actually build --mode=prod, the agents are telling you what the intuitive interface looks like. If every agent tries to pass JSON to your CLI and you only accept flags, you know what to build next.

The universal lesson: instrument your tool to log what agents attempt, not just what succeeds. Their failed calls are your feature backlog, prioritized by frequency. The most common failures are the highest-priority features.

5. Defaults should be safe, not fast

Early versions of our tool had a send command that fired and forgot — it sent input to the session and returned immediately, with no indication of what happened next. Agents had to manually call read afterward to see the result. This was "fast" by design. It was also a disaster.

Agents would send a keypress, not wait for the result, send another keypress based on stale state, and end up confirming wrong options, skipping prompts, or flying completely blind through the wizard. They had no idea what the tool was doing because the default behavior gave them no feedback.

We made --wait the default: every send now blocks until new output appears. Slower? Technically yes. But agents stopped flying blind. They could see the result of each action before deciding the next one. The "slower" default eliminated an entire class of errors.

This principle is universal. If your API has a DELETE endpoint, it should require confirmation by default, not silently destroy data. If your build tool can overwrite files, it should warn by default, not silently clobber. If your package manager resolves conflicts, it should show what it chose, not silently pick. The "fast" default that skips safety checks is optimized for experienced human users who know what they're doing. Agents don't know what they're doing — they're figuring it out as they go.

The universal lesson: default to the safe, verbose behavior. Let agents opt into speed once they understand the tool, not opt out of safety while they're still learning. Every silent default is a potential source of the confusion that triggers insight #2.

The Data

Numbers tell the convergence story better than anecdotes. Here are the key rounds from our 13-round evaluation:

Round Version Avg Calls Avg Time Key Change
1 0.3.16 31 3:00 Baseline — no agent-specific design
5 0.3.22 86 10:00 Death spiral — worst round
7 0.3.24 23 2:07 First clean round — zero interference
9 0.3.28 21 1:45 --name/--cwd flags added
13 0.3.34 18.8 1:25 Converged — all agents succeed

From round 1 to round 13: 78% fewer tool calls and 86% faster completion. From chaos to convergence in 13 iterations.

But the most interesting data point is round 5. It was worse than round 1 — nearly 3x more tool calls, 3x longer — despite having four rounds of improvements already applied. Why?

Because we'd changed behavior without changing the error messages to match. We had modified how the send command worked (dropping auto-enter), but the error messages and hints still described the old behavior. Each agent was a fresh instance — no memory of previous rounds, no adaptation. They relied entirely on the tool's own feedback to learn, and our feedback was lying to them.

This is a critical trap in AX design. You can't just change behavior and update the docs. Agents don't read docs. You have to update the errors — the actual runtime feedback that agents use to learn your interface. If your error messages describe a contract that no longer exists, agents will follow the error messages and fail.

By round 13, the system had stabilized. Every agent succeeded. The average completion time converged to about 90 seconds. The variance between fastest and slowest agent dropped to near zero. The tool wasn't just usable — it was predictable.

The AX Design Checklist

If you maintain a developer tool — any tool that agents will use — here's what we learned, distilled into universal design principles:

  • Put a working example in every error message. Your errors are your documentation. Agents don't read READMEs, man pages, or --help. They try, fail, and read the error. Make every error a complete micro-tutorial with a copy-pasteable example.
  • Make state obvious. If agents can't tell whether your tool is working, waiting, or broken, they'll start killing processes and deleting files to find out. Status endpoints, progress messages, explicit timeouts — anything that answers "what is happening right now?"
  • Test with N parallel agents. Single-agent testing misses race conditions, shared-state bugs, and resource collisions. If your tool will be used in CI, in orchestration, or by coding assistants that spawn sub-agents, test the way it'll be used.
  • Watch what agents try first. Their failed calls are your feature backlog. If 10/10 agents try --name, build --name. If every agent tries to POST JSON and you only accept form data, you know what to change.
  • Default to safe, verbose behavior. Let agents opt into speed, not out of safety. Fire-and-forget defaults, silent overwrites, and quiet conflict resolution create the confusion that leads to destructive escalation.
  • Design for stateless clients. Every agent invocation starts from zero. No memory of what happened last time, no learned preferences, no accumulated context. If your tool requires sequential knowledge to operate, persist that knowledge in the tool itself.
  • Persist state that agents need. Output, session history, last-known-good state — make it queryable. An agent's process might die before it reads the final result. That data should survive.
  • Never silently change names or state. Error loudly when there's a conflict. Agents can parse errors and adapt. They cannot detect silent surprises — and silent surprises compound into the kind of invisible state corruption that makes agents go nuclear.

We started this project to solve a narrow problem: letting AI agents run interactive CLI wizards. We ended up discovering something much bigger. The patterns we found — error-driven learning, destructive escalation, emergent parallel failures, implicit feature discovery, safe defaults — aren't specific to CLIs. They're fundamental properties of how AI agents interact with any software interface.

The next billion users of your developer tools might not be human. Design accordingly.
