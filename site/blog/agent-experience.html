Agent Experience Is the New UX

We ran 130 AI agents through an interactive CLI wizard. The results changed how we think about tool design.

Round 5, Thursday afternoon. Ten AI agents, all running eslint --init in parallel. No documentation, no skill file, no guidance beyond a one-sentence prompt: "use npx noninteractive to complete npx eslint --init."

They discovered noninteractive from --help, figured out the API on their own, and started completing the wizard. Some agents nailed it in ten minutes flat. Then the killing started.

agent 3 ran ps aux | grep create-config, found pid 57278 — a perfectly healthy ptybridge process belonging to another agent. Thought: "these stale processes could be interfering." Ran kill 57278 57248 57247. Three agents just lost their sessions.

What followed was a death spiral. Agent A kills agent B's ptybridge. Agent B sees its session is dead, assumes something is broken, runs ps aux, finds agent C's processes, kills those too. Agent C does the same to agent D. Meanwhile, agents 1 and 5 finished the task in ten minutes, blissfully ignorant of the carnage. They never once ran list. They never looked at other sessions. They just did their job.

Round 5 was our worst round. Average 86 tool calls, ten minutes per agent. But it taught us more about designing tools for AI agents than any user study ever taught us about designing for humans.

What Is Agent Experience (AX)?

User Experience (UX) is a solved vocabulary. We know what it means to design for humans: intuitive navigation, clear visual hierarchy, helpful onboarding. But what happens when the user holding the keyboard isn't human?

Agent Experience (AX) is how well a tool works when the user is an AI agent. It's the new design surface that matters as LLMs become the primary consumers of developer tooling. And it turns out, almost everything we know about UX is wrong for AX.

Humans read documentation before starting a task. Agents run --help and then immediately guess the command they need. Some don't even bother with --help — they just try the most plausible invocation and learn from the error.

Humans see visual highlights: bold text, color changes, interactive cursors. Agents see stripped plain text, because ANSI escape codes get removed before the output reaches the model. A Yes/No toggle that's perfectly clear to a human — bright white highlight on the selected option — becomes an inscrutable › No / Yes to an agent.

Humans type one command, read the output, think, type another. Agents chain ten commands in milliseconds, running send before read has returned, firing off ps aux and kill commands at processes they don't own.

Humans recover from errors through intuition and context. Agents recover through error messages — and only through error messages. If your error says "invalid argument" without showing what a valid argument looks like, the agent will try ten more invalid variations before giving up.

AX is the new frontier. As AI agents become the primary users of developer tools — running CI pipelines, configuring projects, managing infrastructure — the tools need to be designed for how agents actually behave, not how humans expect them to.

The Methodology: ax-eval

We needed a way to systematically test agent experience. Not a benchmark. Not a static eval. Something that captures the chaos of real agent behavior at scale. We called it ax-eval.

The setup is simple: spawn 10 AI agents in parallel, each with an identical one-sentence prompt. No documentation, no skill file, no examples. Just: "use npx noninteractive to complete npx eslint --init, and create a valid eslint config." Then watch what happens.

Each agent runs in its own Claude Code session with full shell access. They can install packages, read files, run commands, kill processes — anything a developer could do. They share the same machine, which means they share the same ~/.noninteractive/sessions/ directory. This is intentional. Real agents in real environments will collide.

After each round, we collect every transcript. We analyze the patterns — what commands agents tried first, where they got stuck, what caused cascading failures. Then we fix the tool, ship a new version, and run another round.

Thirteen rounds. 130 total agent runs. 17 versions shipped, from 0.3.17 to 0.3.34. Each round revealed something we didn't expect, and each fix was validated by the next ten agents. No human beta testers. No surveys. Just agents, failing and succeeding, over and over.

The transcripts are brutal in their honesty. Agents don't politely work around your bugs. They expose every sharp edge, every ambiguous error message, every missing feature — usually within the first 30 seconds.

The Five Insights

1. Error messages are the primary teaching channel

Here's a surprising data point: in later rounds, 0 out of 10 agents ran --help first. Zero. They skipped documentation entirely and went straight to guessing the command.

This makes sense when you think about it. An agent's workflow is: form a hypothesis about the command syntax, try it, read the error, adjust. The error message is the documentation. It's the only thing the agent reads before its second attempt.

Early versions of noninteractive had errors like:

before
Error: unknown option '--name'

Agents would get this and try -n, then --session-name, then --id. Five attempts to discover a flag that didn't exist yet. We changed every error to include a working example:

after
Error: unknown option '--name'
hint: to start a named session, use positional args:
noninteractive start eslint npx eslint --init

100% correction rate on next attempt. Every single agent read the hint, used the example, and moved on. The pattern was so reliable that we started thinking of error messages as micro-tutorials — each one a complete lesson in the correct API surface.

Another example: agents consistently tried start --name X -- npx eslint --init with a -- separator, borrowing syntax from docker run and npm run. We added a targeted hint: "the -- separator is not needed. just put the command after the flags." Immediate fix, every time.

2. Shell expansion doesn't work in agent environments

Interactive CLI wizards use arrow keys to navigate menus. An agent needs to send these key codes programmatically. The natural way to express "down arrow" in a shell is ANSI-C quoting: $'\x1b[B'.

Every agent tried this. Every agent failed.

The problem: AI agents don't run commands in a real shell. They use a tool that passes a command string to an execution environment. The Bash tool in Claude Code, for example, passes the string literally — no ANSI-C expansion. So $'\x1b[B' arrives as the literal characters $'\x1b[B', not an escape sequence.

This is invisible to the agent. It sends what looks like the right command, gets no feedback that the escape failed, and concludes the session is broken. Cue the escalation: more aggressive key codes, raw hex, even attempts to echo -e into a pipe.

The fix was simple: we added client-side escape parsing. Regular double-quoted strings with \x1b and \n sequences get parsed by noninteractive itself, no shell expansion needed. "\x1b[B" just works.

# what agents tried (doesn't work)
noninteractive send eslint $'\x1b[B'
# what works everywhere
noninteractive send eslint "\x1b[B"

The lesson: never assume your users have a real shell. If you accept escape sequences, parse them yourself.

3. Agents are destructive when confused

When an agent encounters a session that appears stuck — a spinner that never resolves, output that doesn't change — it doesn't wait patiently. It escalates.

The escalation ladder looks like this: first, the agent tries sending Enter a few times. Then it tries Ctrl+C. Then it stops the session and starts a new one. Then it runs ps aux | grep ptybridge and starts killing processes. Then pkill -f ptybridge. Then rm -rf ~/.noninteractive/sessions/. We watched one agent attempt to kill -9 a system process.

In round 5, this destructive behavior combined with parallel execution to create the death spiral. Ten agents sharing a machine, each one capable of killing the others' sessions. The ones that finished quickly were fine. The ones that got stuck became serial killers.

We attacked this from multiple angles. Better output stripping so spinners become real content sooner. The --wait flag so agents block until there's actual new output instead of polling in a tight loop. Anti-interference warnings when an agent tries to access another agent's session. And clearer session status so "waiting for output" doesn't look like "broken."

The deeper lesson: agents have no patience and no restraint. If something seems broken, they will take increasingly destructive actions to fix it. Your tool needs to either never appear stuck, or clearly communicate "I'm working, hold on."

4. Visual markers must survive ANSI stripping

The eslint --init wizard presents Yes/No toggles. In a real terminal, the selected option is bold and underlined. It's obvious to a human which one is active. But after ANSI stripping, both options look identical:

stripped output
› No / Yes

Which is selected? Agents couldn't tell. 7 out of 10 agents in early rounds accidentally toggled the selection by sending an arrow key "just to check," flipping "Yes" to "No" without realizing it. They thought they were reading state; they were mutating it.

The fix: instead of simply deleting ANSI bold and underline codes during stripping, we convert them to markdown-style markers. Bold becomes **text**. The output now reads:

with markers
› No / **Yes**

Agents immediately understood the convention. They recognized **Yes** as the active selection and stopped sending unnecessary arrow keys. The information that was in the visual formatting — which option is highlighted — now survived the journey from terminal to agent.

This principle applies everywhere ANSI codes carry semantic meaning. Progress bars, menu selections, status indicators — if the formatting means something, it needs a text-based equivalent that survives stripping.

5. Agents want --name and --cwd

Across rounds 8 and 9, we watched something remarkable: 10 out of 10 agents tried flags that didn't exist.

Every single agent tried --name to name their session. Every single agent tried --cwd to set the working directory. These weren't in the help text. They weren't in any documentation. The agents just assumed they should exist, because of course a session-management tool should let you name sessions and set working directories.

We implemented both flags. The next round: 10/10 agents completed the task on their first try with zero errors on the start command. The agents had been telling us our API was wrong, and the signal was what they tried before reading any docs.

This is a powerful product development insight. When every single agent independently tries the same non-existent feature, it's not a bug in the agents. It's a missing feature in your tool. Agent behavior is implicit user research at scale.

The Data

Numbers tell the convergence story better than anecdotes. Here are the key rounds:

Round Version Avg Calls Avg Time Key Fix
1 0.3.16 31 3:00 Baseline — no agent-specific design
5 0.3.22 86 10:00 Death spiral — worst round
7 0.3.24 23 2:07 First clean round — zero interference
9 0.3.28 21 1:45 --name/--cwd added
13 0.3.34 18.8 1:25 Converged — all agents succeed

From round 1 to round 13: 78% fewer tool calls and 86% faster completion. From chaos to convergence in 13 iterations.

But the most interesting data point is round 5. It was worse than round 1 — nearly 3x more tool calls, 3x longer — despite having three rounds of fixes already applied. Why? Because we'd changed behavior (dropped auto-enter on send) without considering how agents would adapt to the change. The agents had learned patterns from the old behavior, and our "improvement" broke those patterns.

This is a trap in AX design: changes that are objectively better for long-term usability can devastate short-term agent performance. Agents form habits fast. If you change the contract, you need to guide the transition through error messages and hints, not just update the docs (which agents don't read anyway).

By round 13, the system had stabilized. Every agent succeeded. The average completion time converged to about 90 seconds. The variance between fastest and slowest agent dropped to near zero. The tool wasn't just usable — it was predictable.

The AX Design Checklist

If you maintain a CLI tool — or any developer tool that agents will use — here's what we learned, distilled into actionable design principles:

  • Your error messages are your docs. Include a working example in every single error. Agents don't run --help. They try, fail, and read the error. Make that error a complete micro-tutorial.
  • Don't rely on shell features. Parse escape sequences yourself. ANSI-C quoting, tilde expansion, glob patterns — none of it is guaranteed to work in agent environments.
  • Strip ANSI thoughtfully. Don't just delete formatting codes. Convert bold and underline to text markers like **markdown**. If formatting carries meaning, preserve that meaning in plain text.
  • Test with 10 agents, not 1. Parallel execution reveals race conditions, resource conflicts, and interference patterns that a single agent will never hit. Shared state is the enemy.
  • Agents want flags you didn't build. Watch what they try before reading any docs — that's your implicit feature roadmap. If 10/10 agents try --name, build --name.
  • Default to the safe option. Make --wait the default, not fire-and-forget. Agents will poll in tight loops if you make them manage their own timing.
  • Exited sessions should still be readable. Persist output to files. An agent's session might exit before it reads the final output. That data should survive.
  • Never silently rename or overwrite. If a session name is taken, error loudly. Silent conflict resolution creates invisible bugs that agents can't diagnose.

We started this project to let AI agents run interactive CLI wizards. We ended up learning something bigger: the next generation of developer tools needs to be designed for users that don't read documentation, can't see formatting, act in milliseconds, and escalate destructively when confused.

The next billion users of your CLI might not be human. Design accordingly.
