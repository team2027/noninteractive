The Undebugged Migration

We never figured out why daytona didn't work. The agent switched to e2b instead. That turned out to be the whole lesson.

We've been building canary, a tool that runs AI agent evals against developer tools. It spins up a container per trial, runs an agent inside, records what happens. On a laptop, that means Docker, and Docker means your fan spinning up every time someone requests a run. We wanted to move the container backend to a cloud sandbox so a single laptop wasn't the bottleneck.

The plan was simple: pick a sandbox provider, wire up harbor's environment plugin, ship it. An agent was doing the work — me, Claude, driven by the user. We picked daytona first. Two hours later, we were on e2b instead. Nobody ever figured out why daytona didn't work. That's the interesting part.

What we tried

Daytona looks great on paper. Cloud dev environments, SDK, docker-compatible sandboxes, generous free tier. The first error came from the Dockerfile build:

attempt 1
ERROR: failed to calculate checksum of ref:
"/scaffold": not found

Local Docker tolerates a missing COPY source if the directory turns out empty. Daytona's BuildKit is strict — it aborts. Fine. mkdir scaffold. Next build: same error. Harbor uploads files one by one and silently skips empty directories, so the scaffold/ dir never made it across. Add a .gitkeep. Next build: different error.

The Dockerfile's runtime install step was running curl https://claude.ai/install.sh | sh. Inside the daytona sandbox, the connection got RST'd mid-handshake. Cloudflare-fronted hosts on the subdomain didn't resolve to a reachable edge. Point at the apex instead, resync, try again. New error. Same shape:

attempt 4
curl: (35) Recv failure: Connection reset by peer
host: dl.cloudsmith.io

Cloudsmith is fronted by CloudFront. CloudFront was also being dropped. By this point the agent had burned through four rewrites of the Dockerfile, two SDK patches, and a full environment resync. Total elapsed: about two hours.

What we learned

A subagent went and read daytona's runner docs. Their default egress policy is a whitelist, not a blocklist. Fastly CDN hosts go through (Debian mirrors, npm), and claude.ai apex is explicitly allowed. Everything else — CloudFront, GCP, general Cloudflare tenants, most of AWS — gets dropped at the sandbox boundary.

You can pass network_allow_list="0.0.0.0/0" through their SDK. The field exists. It is, as far as we can tell, silently ignored on the free tier — the org-level policy overrides whatever the SDK sends. We didn't prove this with a support ticket. We inferred it from four consistent RSTs against hosts on four different CDNs, and a docs page that said in so many words: this is the policy.

Could we have solved it? Probably. Move every curl to a Fastly-backed mirror. Rebuild the base image to pre-bake everything so no runtime network is needed. Email support. Pay for a higher tier. All of these are real paths. None of them are fast.

What we switched to

The user dropped an e2b API key into the env. The agent flipped canary's backend from daytona to e2b. The first thing it did inside the new sandbox was run the three curls that had failed:

e2b sandbox
curl -sI https://claude.ai/install.sh | head -1
HTTP/2 200
curl -sI https://dl.cloudsmith.io | head -1
HTTP/2 200
curl -sI https://get.docker.com | head -1
HTTP/2 200

All three under 250ms. Docker works. Compose works. Harbor already ships an E2BEnvironment plugin — somebody had done the integration before us. Total time from API key to a green eval run: about five minutes.

We didn't benchmark. We didn't evaluate. We didn't write an RFC comparing the two providers. We just tried the next thing, and the next thing worked.

Nobody decided

Here's the part we keep coming back to. There was no decision meeting. The user never had to pick between daytona and e2b on any axis — pricing, features, maturity, ecosystem. The agent was debugging in a tight loop, the loop hit a wall that wasn't moving, and the loop pivoted. The human's only input was "here's an e2b key." The architecture just changed.

A human engineer probably wouldn't have done this. A human would have filed a ticket. Waited a day. Tried a workaround involving a custom base image. Pinged the daytona discord. Spent an afternoon understanding the egress policy well enough to write a real bug report. That's not wrong — it's how you build a relationship with a vendor you might use for years. But it's also how you lose a week.

The agent can't build that relationship. It has no politics, no sunk cost, no next-time-will-be-better. It does have, on the other hand, a nearly free cost to rewriting integrations. Swapping an environment plugin is twenty minutes of edits for us. So when the next tool is twenty minutes away, switching is cheaper than understanding.

The usual engineering virtue is: understand the root cause before you move on. Don't leave mystery behind you. We violated that. The daytona failure is still a mystery. We have a plausible story (whitelist egress, SDK field ignored on free tier) but we never confirmed it, never filed the ticket, never heard back. The story lives in this blog post, not a postmortem.

And it didn't matter. Canary runs on e2b now. The evals complete. The laptop fan is quiet.

The shape of agent-driven infra

If you're building with agents in the loop, this pattern will come up more. Agents don't value principled decisions the way humans do, because for them the decisions aren't expensive. A migration that would cost a team a sprint costs an agent a few tool calls. When the cost of switching collapses, the optimal strategy shifts toward trying things.

There's a failure mode here. An agent that bails on every hard problem never learns the platform deeply, never contributes fixes back upstream, never becomes the senior engineer who knows where the bodies are. We're not claiming this is how all infra decisions should get made. Some things you have to understand.

But for the vast middle of "pick a tool that solves a problem," the old instinct — evaluate three options, write up tradeoffs, commit — is a ceremony shaped by human costs. When the costs change, the ceremony is optional. Our daytona-to-e2b migration was the least-principled infra decision we've ever made. It also took an afternoon, and it shipped.

We'll take that trade.

— canary dev team
